## 1. 개요

강원도 18개 시·군의 블로그·카페 게시물을 매 시간 수집해 형태소 분석 → 카카오맵 좌표 검증 → 인기도 점수 누적 집계까지 처리하는 Airflow ETL 파이프라인이다. 공공데이터 기반 `tourist_spot`과 독립적으로 `kakao_spot` 테이블을 관리하며, Spring AI 임베딩 파이프라인에 신규 장소를 통지한다.

### 소스 분리 전략

| 항목 | `tourist_spot` | `kakao_spot` |
|------|--------------|-------------|
| 소스 | 공공데이터포털 TourAPI | 카카오 블로그·카페 트렌드 |
| ETL | `travel_daily_incremental` DAG | `popular_spot_collection` DAG |
| 갱신 | 매일 00:05 KST | 매 정각 KST |
| AI 임베딩 | Spring이 처리 후 `spot_embedding` 저장 | 동일 (`kakao_spot_id` FK 컬럼으로 구분) |
| 사용자 노출 | 관광지 목록 | "요즘 핫한 곳" 별도 섹션 |

## 2. 아키텍처

```
[popular_spot_collection — 매 정각 KST]

Kakao Daum 검색 API (최신순)
  (블로그·카페 × 3쿼리 × 18도시, 채널·쿼리당 최대 2페이지)
        │
        ▼ 신규 URL만 원천 JSON 스냅샷 저장
        │  data/trend/raw/{date}/raw_{run_id}.json
        │ 이전 실행에서 수집한 URL을 만나면 해당 검색어·채널 중단
        ▼
kiwipiepy 형태소 분석 (NNP·NNG)
  + 불용어·지역명 exact match 제거
  + 채널 다양성 보너스 (blog+cafe × 1.3)
  + 출현 빈도 ≥ 3 필터 / 상위 20개
        │
        ▼ 집계 JSON 저장 + trending_spot UPSERT
        │  data/trend/raw/{date}/aggregated_{run_id}.json
        ▼
카카오맵 로컬 API (키워드 검색)
  + 카테고리 검증 AT4·FD6·CE7·AD5
  + 검증 성공 → kakao_spot UPSERT (score 누적)
  + 신규 장소 → Spring 임베딩 파이프라인 통지
        │
        ▼
[popular_spot_decay — 매일 00:00 KST]

kakao_spot 전체 감쇠:
  AT4·AD5 × 0.85 (~30일 소멸)
  FD6·CE7 × 0.70 (~13일 소멸)
score < 0.01 → 자동 삭제
```

## 4. DAG 상세

### 4-1. popular_spot_collection (매 정각 KST)

| 태스크 | 역할 | 입력 | 출력 (XCom) |
|--------|------|------|-------------|
| `start_run` | etl_run 레코드 생성 | - | `{run_id}` |
| `collect_search_texts` | Kakao 최신순 검색 API 기본 최대 216 req | run_id, logical_date | `{raw_path, api_calls, ...}` |
| `analyze_and_aggregate` | 형태소 분석 + trending_spot 저장 | raw_path (XCom) | `{aggregated_path, total_keywords, ...}` |
| `validate_and_promote` | 카카오 로컬 API ≤360 req + kakao_spot upsert | aggregated_path (XCom) | `{promoted, new_spot_ids, api_calls, ...}` |
| `notify_spring_embedding` | 신규 장소 Spring 통지 | new_spot_ids (XCom) | `{notified, accepted}` |
| `finalize` | etl_run 완료 기록 (trigger_rule=all_done) | 전 태스크 XCom | etl_run 갱신 |

**태스크 간 데이터 전달**  
- XCom 에는 파일 경로(문자열)만 전달한다. 원천·집계 JSON 은 `data/trend/raw/{date}/` 에 저장한다.
- `new_spot_ids` 는 신규 insert 된 kakao_spot.id 목록이므로 건수가 적어 XCom 에 적합하다(최대 360개).

**멱등성**  
- `collect_search_texts`: 같은 execution_date·run_id 의 스냅샷이 이미 있으면 API 호출 없이 재사용한다.  
- `upsert_kakao_spots`: `ON CONFLICT (kakao_place_id) DO UPDATE` — 재실행 시 점수가 중복 가산된다. 재실행이 필요한 경우 수동으로 점수를 보정하거나 배치를 건너뛴다.

**API 요청 수 (시간당)**

| 단계 | 건수 |
|------|------|
| 블로그 검색 | 54 req (18 × 3) |
| 카페 검색 | 54 req |
| 카카오 로컬 검증 | ≤ 360 req (18 × top_n=20) |
| **합계** | **≤ 468 req/h** |

> 카카오 기본 할당량 10,000 req/day ≒ 416/h. 피크 초과 시 `TREND_TOP_N=15` 로 낮추거나 `TREND_CITY_SLEEP_SEC` 를 늘린다.

| 태스크 | 역할 |
|--------|------|
| `start_run` | etl_run 레코드 생성 |
| `apply_decay_and_prune` | 카테고리별 감쇠 계수 곱하기 → score < 0.01 삭제 |

| 7일 | 0.32 | 0.08 |
| 13일 | 0.14 | **< 0.01 → 삭제** |
| 30일 | **< 0.01 → 삭제** | — |

## 5. DB 스키마

### trending_spot

```sql
CREATE TABLE trending_spot (
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    keyword         VARCHAR(100) NOT NULL,
    city_name       VARCHAR(20)  NOT NULL,
    blog_frequency  INTEGER      NOT NULL DEFAULT 0,
    cafe_frequency  INTEGER      NOT NULL DEFAULT 0,
    multi_channel   BOOLEAN      NOT NULL DEFAULT false,  -- 채널 다양성 보너스 여부
    promoted        BOOLEAN      NOT NULL DEFAULT false,  -- kakao_spot 승격 여부
    collected_at    TIMESTAMP(6) NOT NULL DEFAULT now(),
    CONSTRAINT uk_trending_keyword_city UNIQUE (keyword, city_name)
);
```

- **목적**: 형태소 분석 중간 집계. 사용자에게 직접 노출되지 않음.
- **라이프사이클**: 수집마다 upsert. `promoted=false` 레코드는 다음 배치에서 재검증 대상.

### kakao_spot

```sql
CREATE TABLE kakao_spot (
    id                   BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    kakao_place_id       VARCHAR(30)      NOT NULL,       -- 카카오맵 장소 ID (UK)
    place_name           VARCHAR(200)     NOT NULL,
    city_name            VARCHAR(20)      NOT NULL,
    address_name         VARCHAR(300),
    category_group_code  VARCHAR(10)      NOT NULL,       -- AT4·FD6·CE7·AD5
    category_group_name  VARCHAR(50),
    longitude            DOUBLE PRECISION NOT NULL,
    latitude             DOUBLE PRECISION NOT NULL,
    blog_mention_count   INTEGER          NOT NULL DEFAULT 0,  -- 누적 언급 수
    cafe_mention_count   INTEGER          NOT NULL DEFAULT 0,
    popularity_score     DOUBLE PRECISION NOT NULL DEFAULT 0,  -- 누적 가산 후 매일 감쇠
    collected_at         TIMESTAMP(6)     NOT NULL DEFAULT now(),
    CONSTRAINT uk_kakao_place_id UNIQUE (kakao_place_id)
);
```

- **인기도 점수 공식**: `popularity_score += normalized_score` (배치당 최댓값 정규화)
- **채널 다양성 보너스**: `raw_score = (blog_freq + cafe_freq) × 1.3` (두 채널 모두 언급 시)

### spot_embedding (변경)

```
변경 전: content_id BIGINT PRIMARY KEY
변경 후: embedding_id BIGINT IDENTITY PRIMARY KEY
         content_id   BIGINT nullable (tourist_spot FK)
         kakao_spot_id BIGINT nullable (kakao_spot FK)
         CHECK (num_nonnulls(content_id, kakao_spot_id) = 1)
```

두 소스의 임베딩을 하나의 테이블에서 관리한다. AI 추천은 소스 구분 없이 embedding 벡터만 코사인 유사도로 조회한다.

| `TREND_DECAY_RESTAURANT` | FD6 감쇠 계수 | `0.70` |
| `TREND_DECAY_CAFE` | CE7 감쇠 계수 | `0.70` |
| `TREND_SNAPSHOT_DIR` | 원천·집계 JSON 저장 디렉터리 | `data/trend/raw` |

```powershell
# 환경변수에서 DB URL 읽기
$url = (Select-String -LiteralPath 'docker/.env' -Pattern '^TRAVEL_DB_URL=').Line.Substring('TRAVEL_DB_URL='.Length)

# 기존 스키마 초기화 (신규 환경만)
psql $url -v ON_ERROR_STOP=1 -f database/migrations/000_initialize_travel_schema.sql

# etl_run 복합 PK 마이그레이션 (신규 환경만)
```

## 11. 설계 결정 사항

### 왜 trending_spot 을 중간 테이블로 유지하는가?

카카오맵 로컬 API 검증 실패(카테고리 불일치, 좌표 범위 초과)가 발생해도 수집된 키워드 데이터를 보존하기 위해서다. `promoted=false` 레코드는 디버깅, 통계, 추후 재검증에 활용할 수 있다.

### 왜 popularity_score 를 누적 가산하는가?

점수를 매 배치마다 덮어쓰면 "지금 이 시간의 인기도"만 반영된다. 누적 가산 + 일일 감쇠 방식은 **지속적으로 언급되는 장소는 상위권을 유지**하고, **언급이 끊긴 장소는 자연 소멸**하도록 설계한다.

### 왜 spot_embedding PK 를 서로게이트 키로 바꾸는가?

기존 `content_id BIGINT PRIMARY KEY` 는 `tourist_spot` 과 1:1 이었지만, `kakao_spot` 을 추가로 지원하려면 복수의 소스를 하나의 테이블에서 수용해야 한다. 서로게이트 PK + partial unique index 조합이 가장 명확한 접근이다.

### MinIntervalLimiter 를 core/ 로 이동한 이유

`travel_etl` 과 `trend` 두 도메인이 동일한 pacing 로직을 사용하므로 "2번 이상 반복되면 공통 모듈로 추출" 원칙에 따라 `src/core/rate_limiter.py` 로 이동했다. 기존 `travel_etl/service/rate_limiter.py` 는 하위 호환 재내보내기로 유지된다.
